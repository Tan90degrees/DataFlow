# ADR 0004：持久期望状态与幂等外部协调

[English](../../adr/0004-idempotent-reconciliation.md) | 简体中文

## 状态

已接受

## 背景

DataFlow 必须在控制器重启、Kubernetes API 重试、重复协调调用和外部 RayJob 完成时不丢失工作流历史或创建重复工作。PostgreSQL 已存储不可变流水线版本、执行单元、只追加尝试和状态转换事件。KubeRay RayJob 是外部对象，其生命周期可能长于任一控制器进程。

如果控制器将内存状态或 Kubernetes create 调用返回值视为权威，就无法避免崩溃窗口。例如进程可能成功创建 RayJob，却在记录该事实前崩溃；使用随机对象名重试会创建重复执行。

## 决策

PostgreSQL 继续作为持久期望状态事实来源。调度器与协调器职责分离：

- 调度器评估静态 DAG 依赖，只有全部上游单元为 `SUCCEEDED` 时，才把 `PENDING` 单元变为 `READY`；
- 协调器通过 `Executor` 接口观察一个持久执行单元，并使其与外部作业收敛；
- 重试创建新的只追加执行尝试，不修改或复用已完成尝试；
- 先持久化取消运行，再向等待单元和活跃外部作业传播。

KubeRay 对象标识由 `(run_id, unit_id, attempt_number)` 确定。即使 DNS 名称必须缩短，也会保留尝试后缀，并用哈希使长标识抗冲突。`submit` 是幂等的：先观察确定性对象，只在不存在时创建，并处理并发控制器的冲突。

关键提交顺序：

1. 把单元状态持久化为 `SUBMITTING`；
2. 追加持久尝试并将其持久化为 `SUBMITTING`；
3. 提交或观察确定性外部对象；
4. 根据外部状态收敛尝试和单元状态。

无论在哪一步崩溃，下一个控制器都能从持久运行/单元/尝试数据派生相同外部标识并恢复观察。尝试从未进入 `RUNNING` 前对象缺失时，可用同一尝试标识安全重提；进入 `RUNNING` 后对象缺失视为外部故障，如果可重试则创建新尝试。

外部 API 可用性错误不会自动消耗工作流重试，而会将持久尝试/单元移到 `UNKNOWN`，让协调器重新观察同一确定性对象。终态外部执行故障使用显式重试策略和退避；重试会使用新确定性 RayJob 名称创建新尝试。

## 影响

- 重复协调不会为同一尝试创建重复 RayJob。
- 控制器重启无需本地内存即可找到已有 RayJob。
- 快速作业可能从 `SUBMITTING` 直接变为 `SUCCEEDED`，因为首次观察时已经终止。
- 取消可安全重试，因为外部删除幂等，持久运行已经是 `CANCELLED`。
- 控制循环以后可以水平复制，但效率方面仍可能需要更强的工作认领/选主策略。
- 制品提交语义保持独立；成功 RayJob 本身不定义持久制品事务。
