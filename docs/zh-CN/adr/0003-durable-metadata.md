# ADR 0003：PostgreSQL 是持久编排的事实来源

[English](../../adr/0003-durable-metadata.md) | 简体中文

## 状态

已接受

## 背景

从工作流引擎角度看，Ray task、RayJob、RayCluster、控制器进程和 Kubernetes Pod 都是临时的。DataFlow 必须能在控制面重启后，不依赖在线 Ray 对象引用或内存调度队列，判断原本意图、已经发生的操作以及仍需协调的工作。

重试也要求历史尝试保持可检查。如果用下一次尝试覆盖上一次，会让故障分析和幂等协调变得不可靠。

## 决策

PostgreSQL 是编排元数据的持久事实来源。初始模式持久化：

- 流水线和不可变流水线版本；
- 流水线运行；
- 物理执行单元；
- 只追加执行尝试；
- 面向 UI/可观测性的节点级运行投影；
- 状态转换和生命周期操作的只追加事件。

PipelineSpec 以 JSONB 存储，并带有规范 SHA-256 哈希。版本分配会先锁定所属流水线记录，再选择下一个版本号，从而实现串行化。

运行、执行单元和尝试使用独立状态机。状态转换会锁定聚合记录、验证转换、更新聚合，并在同一数据库事务中追加对应事件。调用方可以提供期望当前状态以检测陈旧控制器决策。

数据库触发器保护 `pipeline_versions` 和 `events` 不受 UPDATE 或 DELETE。每次执行尝试总会获得新记录和单调递增尝试号，历史尝试永不覆盖。

模式变更以有序 SQL 迁移随 Python 包分发。执行迁移时使用 PostgreSQL 事务级咨询锁，因此多个控制面副本可以安全并发启动。

## 影响

- 调度器和协调器可在进程重启后恢复非终态执行单元。
- Kubernetes/Ray 状态可视为外部观测状态，并与 PostgreSQL 协调。
- 持久工作流语义不依赖 Ray `ObjectRef`、驱动内存或 Pod 生命周期。
- PostgreSQL 成为必需控制面依赖，并由 CI 集成测试覆盖。
- 事件历史是审计流，不是可变投影；派生视图应从聚合表或事件重建，而不是重写历史事件。
