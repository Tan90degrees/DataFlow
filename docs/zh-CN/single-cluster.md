# 执行架构

[English](../single-cluster.md) | 简体中文

## 职责

DataFlow 在调用它的 Python 进程中校验静态数据/控制 DAG 并驱动 Ray Data，不创建 driver 进程或集群。
Ray 负责 task/actor 放置和数据块传输，Ray Data 负责流式执行、融合与背压。
所有工作指向一个已有集群，其生命周期和依赖归平台管理。

`run_pipeline` 执行单个 DAG；`PipelineRunner` 复用一个连接、固定 DAG 协调线程和一个共享节点线程池，
承载多个 DAG。这些线程负责构图和等待 Ray，业务数据计算仍在 Ray task/actor 中执行。
没有数据库、独立服务、按任务建集群或中间制品协议。

## 依赖推进

节点等待所有前驱完成。普通变换的完成表示惰性 Dataset 计划构建完成，下游仍可融合与流式执行；
显式缓存节点和控制依赖源需物化完成后才放行后继，writer 需等最终写入返回。
独立节点和 sink 按节点并发上限同时执行，协调器等待完成通知，不轮询。

每个活动 DAG 最多持有 `max_concurrent_nodes` 个节点 Future；共享 runner 在全局同时执行不超过这个数量的动作，
其有限节点队列上界为活动 DAG 数乘该上限。协调器等待依赖时不占节点执行线程，避免嵌套线程池互相等待。
并发消费前复制 Dataset 句柄，不复制数据块。不要并发修改 Ray DataContext 或调用方规格。

## 共享与汇合

分支默认保持惰性，各消费者可能重算共享前缀。这避免自动的整份数据屏障，有利于流式执行，
但可能增加大量重复计算。UDF 应允许重算和重试，避免在变换中产生非幂等副作用。
昂贵公共前缀使用 `.cache()`，在单次运行中物化一次并复用数据块。
缓存是执行与内存取舍，不是持久状态，也不是自适应内存预算。

控制边要求源节点完成后才能构建目标。变换作为控制源时，即使没有 `.cache()` 也会物化；
writer 作为控制源时写入已经完成。控制边不传数据，SDK 用 `flow.after(source, target)` 定义。

`union` 按显式输入端口顺序追加两个以上同 schema 输入的行，不按位置对齐、不去重。
会检查列名和类型，schema 发现可能触发 Ray 采样。`join` 对两个输入按明确的键和关联类型汇合，
端口 0 为左表，1 为右表，使用 Ray 的 hash shuffle，可能物化输入并消耗较多内存。
二者都不是按位置 zip，也不是任意 Python 多输入回调。

## 上限与失败

runner 使用物理有界队列，满时 `submit` 阻塞或超时。
`iter_completed` 按活动加排队容量限制输入消费，按完成顺序返回输入序号和结果，不内部累计所有历史结果。
排队任务取消后，仍占物理队列容量，直到 worker 将其移除。

观察到节点失败后停止推进新后继，尽量取消未开始的节点动作，等待已启动动作结束后报告失败。
其他通过独立 submit 提交的 DAG 可以继续。批量迭代器观察到失败后停止补充输入，
取消排队 DAG 并等待已启动工作结束；已经开始的写入不会被强制杀死。

Ray 可能通过网络传输块，也可能 spill 到配置的本地磁盘；DataFlow 不配置远程 spill 或 S3 中转。
缓存、join shuffle 和多个并发流水线仍可能超出内存。这里的上限约束准入和驱动动作，
不是操作系统堆内存或全部 Ray 任务队列的硬限制，actor 资源申请仍需符合实际集群容量。

宿主负责请求持久化、最终写入幂等和 driver 重启恢复。不承诺跨 sink 原子提交、工作流 exactly-once、
全局最优公平性、跨 DAG 模型 actor 池或自动内存感知准入。参见[运维](operations.md)和[性能边界](performance.md)。
